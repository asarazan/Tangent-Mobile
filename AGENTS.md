# AGENTS.md — Tangent Mobile

Agent-facing guide to this repository. Read this before making changes.

## What this project is

**Tangent** is a Kotlin Multiplatform (KMP) Mastodon client. The Android app is a real, working
client (Compose UI); the iOS app is still the untouched KMP template stub.

Just as important: Tangent is deliberately a **testbed**, and always has been. Optimize for that
meta-purpose, not just for shipping a Mastodon client:

- **[martok](https://github.com/asarazan/martok)** — the Mastodon API entities in `shared/` are
  generated from TypeScript schemas by martok (see *Schema pipeline* below). This repo was partly
  built to exercise martok.
- **[articulate](https://github.com/asarazan/articulate)** — Android `strings.xml` → Xcode String
  Catalog conversion. Tangent's dual-native future makes it a natural adoption candidate once the
  SwiftUI app has real user-facing copy.
- **Automated SDLC** — the repo is a proving ground for agent-driven development loops (Warp
  Software Factories, Oz, Claude Code, etc.). **GitHub issues are the source of truth for work
  items.** Issues should be well-scoped with acceptance criteria; agents pick them up.
- **[Parive](https://parive.ai/)** — iOS/Android parity analysis. Tangent starts at maximal drift
  (finished Android, stub iOS); Parive runs measure progress as iOS catches up.

## Strategic decisions (settled — don't relitigate)

- **iOS strategy: SwiftUI-native UI on shared KMP viewmodels.** NOT Compose Multiplatform. The
  shared MVI layer (`SharedViewModel` typealiases) exists precisely so SwiftUI can bind to it.
  CMP would hollow out the testbed value (articulate and Parive both require two native codebases).
- **GitHub issues over any local issue tracker**, because the external SDLC tooling speaks GitHub.
- **Default branch is `dev`.** PRs target `dev`.

## Module map

```

build_schema.sh         Regenerates Kotlin entities from the schemas via martok
shared/                 KMP library (commonMain / androidMain / iosMain)
  api/                  Api.kt (Ktorfit interface), Ktorfit.kt (client factory)
  api/entities/         GENERATED by martok — never hand-edit; edit the .d.ts and regen
  api/mock/             MockApi for previews/tests
  sdk/                  Domain layer: Mastodon, MastodonServer, credentials, timeline
  data/                 SQLDelight timeline cache (TimelineStorage, mappers)
  viewmodel/            Shared MVI viewmodels: Login, Home, Timeline
  viewmodel/base/       MobileViewModel (MVI core), SharedViewModel interface
  koin/                 initKoin()
  fakes/                Fake data for previews/tests
androidApp/             Compose UI app (the finished platform)
  activity/             MainActivity (router), LoginActivity, HomeActivity
  compose/              Screens + status rendering (attachments, HTML, custom emoji)
  html/                 TangentHtml (jsoup → AnnotatedString), Emojify
iosApp/                 SwiftUI STUB — CocoaPods-integrated `shared` framework, renders a greeting

```

`shared` is wired into the iOS app via the Kotlin `cocoapods` plugin + `iosApp/Podfile`
(pod name `shared`).

## Architecture

### MVI contract (the load-bearing abstraction)

`MobileViewModel<State, Event, SideEffect>` in `shared/.../viewmodel/base/`:
- Single `reduce(event, currentState): State` suspend function; state exposed as `StateFlow`.
- One-shot effects via `sideEffectFlow` (navigation, toasts, URL launches).
- Each VM exports a `typealias SharedXViewModel = SharedViewModel<State, Event, Effect>` — this is
  the surface iOS/SwiftUI should bind to.
- Android binding: `AndroidViewModel` wraps a shared VM in an AndroidX `ViewModel` with
  `viewModelScope` (see `shared/src/androidMain/.../viewmodel/`). iOS needs an equivalent wrapper
  (ObservableObject bridging `StateFlow` → `@Published`); none exists yet.

### Domain/SDK layer

- `MastodonServer` — per-domain: app registration (`/api/v1/apps`), OAuth token exchange.
  OAuth redirect URI: `tangentsocial://tangent.social/redirect` (Android intent-filter handles it).
- `Mastodon` — an authenticated account session (account id + server + token). Multiple accounts
  are supported at the storage layer (`MastodonStorage`), though the UI always picks the first.
- Persistence is two-tier:
  - `MastodonStorage` / `ServerCredentials` — accounts & app credentials as JSON blobs in
    `multiplatform-settings` (SharedPreferences / NSUserDefaults).
  - `TimelineStorage` — per-account SQLDelight DB (`TangentDatabase`, table `DbStatus`) caching
    whole `Status` objects as JSON columns, with `load_more` placeholder rows marking pagination
    gaps and a denormalized `reblogs` column so a status update can be propagated into boosts
    that wrap it. Optimistic fave/reblog with server refetch (server counts lag).

### Networking

Ktorfit (Retrofit-style, KSP codegen) over Ktor client (OkHttp on Android, Darwin on iOS),
kotlinx.serialization JSON. The `Api` interface covers: instance info, app auth, OAuth token,
public + home timelines, verify credentials, fave/unfave, reblog/unreblog, get status by id.

### Schema pipeline (martok)

```
./build_schema.sh   # deletes shared/.../api/entities and regenerates from api/entities/*.d.ts
```
Requires the `martok` CLI. Rules:
- Never hand-edit `shared/src/commonMain/kotlin/social/tangent/mobile/api/entities/` — changes go
  in the `.d.ts` files, then regen.
- The `.d.ts` files carry full Mastodon doc comments; they double as API reference.

### Android UI notes

- Pure Compose (Material 2). Status HTML is parsed with jsoup (`TangentHtml`) into
  `AnnotatedString` with custom span/annotation handling; custom emoji are inlined via
  `EmojiText`/`Emojify`; images via Coil (+ blurhash placeholder decoder vendored from Wolt).
- Attachment layouts are count-specific (`MonoImage`…`QuadImage`).
- `buildSrc/Instances.kt` fetches the top instances.social hosts and generates Android
  intent-filters (the `AUTO-GENERATED FILTERS` block in the manifest) so verified links open the
  app. Needs `INSTANCES_SOCIAL_API_KEY` env var; manual, run rarely.

  the *account* `id` instead of `status.id`. They appear to be dead code: the live path is

## CI

GitHub Actions workflow: [`.github/workflows/ci.yml`](.github/workflows/ci.yml).

- **Triggers:** push to `dev` or `main`, pull requests targeting `dev`, and manual dispatch.
- **`android` job** (ubuntu-latest): `./gradlew :androidApp:assembleDebug :androidApp:testDebugUnitTest`.
  On failure, test reports are uploaded as a build artifact.
- **`ios` job** (macos-latest): builds the shared Kotlin/Native framework
  (`:shared:linkDebugFrameworkIosSimulatorArm64`), runs `pod install`, then builds the SwiftUI
  stub app via `xcodebuild` (code signing disabled). `~/.konan` is cached across runs.
  - **Explicit-module scan workaround:** CocoaPods integrates the KMP framework through a
    `[CP-User] Build shared` run-script phase with no declared outputs, which shells out to
    `./gradlew :shared:syncFramework`. On a clean checkout, Xcode's explicit-module dependency
    scan can run *before* that script phase populates `shared/build/cocoapods/framework` (the
    path the generated `Pods-iosApp` xcconfig searches), producing a spurious
    `unable to resolve module dependency: 'shared'` build failure even though the script phase
    itself succeeds moments later. The workflow works around this by invoking the equivalent
    `:shared:syncFramework` task for both simulator archs (`arm64 x86_64`) itself, before
    `pod install`/`xcodebuild` ever run, so the framework already exists on disk when Xcode's
    scan happens. This didn't reproduce in local builds, likely because local `DerivedData` is
    rarely fully clean.

Both jobs must stay green on the pinned toolchain versions in `buildSrc/Deps.kt` — do not bump
dependencies to fix a CI failure; fix the workflow or the code instead.

## Conventions

- Versions live in `buildSrc/Deps.kt`; add new deps there, not inline.
- Package root: `social.tangent.mobile` (shared), `social.tangent.mobile.android` (app).
- Shared VMs must stay platform-agnostic: no Android imports in `commonMain`; platform behavior
  goes through `expect`/`actual` (`Platform.kt`) or the side-effect channel.
- Generated code (`api/entities/`) is committed, but never edited by hand.
- Tests: parser-level tests live in `androidApp/src/test/`; shared code has test scaffolding
  (koin-test) but no meaningful coverage yet — new shared logic should add commonTest coverage.
